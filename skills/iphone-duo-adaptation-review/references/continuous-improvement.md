# 自测、复盘与持续改进

目标是降低有证据的漏报、误报和交付丢失。这里的“成长”是对可复用执行方法的版本化改进，不是模型参数训练，也不意味着每轮必须修改 skill。

## 完成条件

截图及规范环节集中完成清晰全页巡检，确认质量并重点回查问题与疑点；入口核对发生页面、问题区域、编号、示例去重、统计和实际发布内容一致。实际巡检和修订记录保存在本次项目，不能用模板自动填成通过。交付前完成这些检查与发现的修正；发布回读发现遗漏或排版错误时先修正再宣告完成。

## 每轮复盘

每次审查保存 retrospective.json，包括本轮证据/skill 版本、自测与用户纠错发现、已纠正结果、执行原因、方法改进候选及处理结果。未发现方法缺口时也记录“本轮无证据支持的新改进”，不能声称绝无遗漏。后续用户反馈补入同一项目复盘并保留修订历史。

按实际责任定位：

|问题|负责更新的 skill|核对证据|
|---|---|---|
|漏状态、误去重、补帧不足、裁边或脱敏损伤|app-video-page-capture|视频片段、候选分类、原图与受审图|
|漏组件、漏实例、裁切漏报、适用条件或例外误判|iphone-duo-design-guidelines|原图区域、实例检查、官方原文与例外|
|归类重复、发生页丢失、标注或计数错误、交付不一致|iphone-duo-adaptation-review|review 与 report、发布映射及回读|

区分规则覆盖不足与执行未落实：已有规则覆盖但漏看时，改实例识别、自测或证据记录方法；不要重复新增规则，也不要把一次误判写成某个业务页面必错。原因不明时保存已观察到的差异，不编造原因。

## 通用改进的入库条件

1. 用原始证据核实缺陷或误判，明确缺口发生在哪个环节。
2. 提炼能用于不同流程和录屏的检查动作、判断条件或交付约束。页面名、截图编号、数量、图片、具体问题清单和临时配置留在项目，不进入 skill。
3. 先检索现有说明：能修正文句或补充执行方法时不再另建重复规则。执行方法与苹果标准分开；更改规范判据必须有对应官方原文、适用条件与例外。
4. 用导致该改进的案例验证能检出问题，再用容易混淆的正常案例验证不会误报。遇到规则条件变化，核对相应官方来源。若缺少有效反例，保留候选，不把未经验证的要求升级为强制规则。
5. 备份受影响文件，做最小修改，检查入口能找到新增参考，运行对应校验；脚本变化另做实际输入输出验证。回查本次受影响结果，记录改进前后判断和方法版本，验证不成立则恢复备份。

具体回归样本与历史证据映射保存在项目测试目录，记录图片路径/hash、期待判断、依据及观察结果；不用把案例装入通用 skill。用户已授权持续改进的任务内可以更新，实际写入仍遵循文件和工具权限。不得自动扩大审查范围、制造苹果要求或更新其他用户文档。

## 向用户说明

报告正文只展示读者所需问题与依据。任务结束在对话中简短说明实质纠正和已经验证的 skill 改进；自测细表、候选和执行日志留在后台。未完成的验证不宣称完成。
